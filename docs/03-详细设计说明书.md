## 3 模块详细设计

### 3.1 鉴权与授权

#### 3.1.1 四种凭证

| 主体 | 凭证 | 适用路由 | 校验函数 |
|---|---|---|---|
| 匿名 | 无 | `/health`、`/shop/products`、`/shop/categories` | — |
| 登录用户 | `Authorization: Bearer <JWT>` | `/api/*`、`/shop/*` 读写 | `require_user`（中台校验 JWT） |
| 服务 | `X-Service-Token` | 中台 `/`、`/shop/*` | `require_service_token` |
| 运营 | `X-Operator-Token` | `/shop/admin/*` | `require_operator` |

#### 3.1.2 数据结构

```python
@dataclass(frozen=True)
class AuthContext:
    kind: Literal["anonymous", "user", "service", "operator"]
    subject: str                 # 登录名 / "service:agent" / "operator"
    cuid: str | None = None      # 商城账号，如 "u1001"；用于对象归属校验
```

#### 3.1.3 函数清单（中台 `app/security.py`，约 150 行）

| 函数 | 签名 | 行为 | 异常 |
|---|---|---|---|
| `validate_settings` | `() -> None` | 在 `app.py` **模块导入时**调用：`AUTH_ENFORCE=on` 且缺 `SERVICE_TOKEN`/`OPERATOR_TOKEN` → `RuntimeError`；`APP_ENV=prod` 且 `AUTH_ENFORCE=off` → `RuntimeError` | `RuntimeError` |
| `effective_mode` | `() -> str` | 返回 `on/warn/off`；`warn` 且 `AUTH_WARN_SINCE` 超过 24h → 返回 `on` 并打 `auth.warn_expired` | — |
| `require_service_token` | `(x_service_token: str \| None = Header(None)) -> AuthContext` | `None` → 401；`secrets.compare_digest(v.encode(), expected.encode())`（bytes 版，规避非 ASCII 的 TypeError） | 401 |
| `require_user` | `(creds: HTTPAuthorizationCredentials \| None = Depends(optional_bearer)) -> AuthContext` | 用 `pyjwt` 解码 `JWT_SECRET_KEY`，`algorithms=[settings.jwt_algorithm]`、`options={"require":["exp","sub"]}`；取 `sub`、`cuid`。**`cuid` 缺失直接 401「身份已过期，请重新登录」，禁止回落默认账号** —— 回落会让所有存量 token 变成同一个商城账号，比修复前更容易越权 | 401 |
| `require_metrics_token` | `(x_metrics_token: str \| None = Header(None)) -> None` | 独立令牌，仅保护 `/metrics` | 401 |
| `require_service_or_user` | `(req: Request) -> AuthContext` | **不用 `_check` 包装**：内部先取 header 判定令牌存在性，再分派到上述函数；两者都失败 → 401 | 401 |
| `require_operator` | `(x_operator_token: str \| None = Header(None)) -> AuthContext` | 静态令牌比较；失败 403 | 403 |
| `assert_self_or_service` | `(ctx: AuthContext, user_id: str) -> None` | `kind in ("service","operator")` 放行；否则 `ctx.cuid != user_id` → 403 | 403 |

> `optional_bearer = HTTPBearer(auto_error=False)`：**必须关掉 auto_error**，否则缺头返回 403 而非设计要求的 401。

#### 3.1.4 挂载（避开内置路由陷阱）

```python
# app/app.py —— 注意保留 prefix，且 public 路由先注册
app.include_router(shop_public_router, prefix="/shop")                     # 匿名读，无依赖
app.include_router(shop_router, prefix="/shop",
                   dependencies=[Depends(require_service_or_user)])
app.include_router(shop_after_sale_router, prefix="/shop",
                   dependencies=[Depends(require_service_or_user)])
app.include_router(shop_admin_router, prefix="/shop/admin",
                   dependencies=[Depends(require_operator)])
# 根 router 只对业务路径挂服务令牌；/health 单独用 @app.get 注册，不挂依赖
app.include_router(router, dependencies=[Depends(require_service_token)])
```

**必须遵守的三条约束**（审查发现，否则线上事故）：

1. `/health` 必须**匿名**：**从 `app/api.py` 删除现有 `/health` 路由**，改在 `app/app.py` 中 `include_router` **之前**用 `@app.get("/health")` 注册。原因：Starlette 按注册顺序匹配，`app/api.py:123` 的版本先注册，后面再追加同名路由会被遮蔽，仍走带依赖的那条 → 401 → 容器永久 unhealthy。`app/api.py` 必须列入 §8.2 修改清单。
2. backend 的 healthcheck 当前打 `/docs`（`F-17`），**必须改为 `/health`**，并在 Agent 新增匿名 `GET /health`（返回 `{"status":"ok"}`）。
3. `/docs`、`/openapi.json`、`/metrics` 是 **app 级路由，router 依赖管不到**：`/docs` 用 `docs_url=None, redoc_url=None, openapi_url=None`（`APP_ENV=prod` 时）直接关闭；`/metrics` 用 `@app.get("/metrics", dependencies=[Depends(require_metrics_token)])` 单独挂。

> `dependencies=[]` **不能**用来做匿名豁免（依赖是加法合并），所以公开接口必须拆到独立的 `shop_public_router`，并从 `shop_router` 中真正删除 `/products`、`/categories`，避免同路径双注册。

#### 3.1.5 `AUTH_ENFORCE` 行为

| 取值 | C 端读写 | `/shop/admin/*` | 生产环境 |
|---|---|---|---|
| `on`（默认） | 校验，失败 401 | 校验，失败 403 | 允许 |
| `warn` | 失败记 `auth.would_block` 后**放行**（actor 记为 `warn-mode:<ip>`） | **仍 403（失败关闭）** | 允许，≤24h |
| `off` | 放行 | 放行 | **启动失败** |

`warn` 的起止时间从 `AUTH_WARN_SINCE`（ISO8601，env）读，**不存进程变量**（重启即重置的问题由此规避）；超 24h 后 `effective_mode()` 返回 `on` 并打 `auth.warn_expired`，同时导出 gauge `auth_warn_mode`。

#### 3.1.6 对象级授权（D2=B）

新增 `app/ownership.py`：

```python
def get_order_for(ctx: AuthContext, db: Session, order_id: str) -> models.Order:
    order = _load_order(db, order_id)
    # 统一 403，不用 404：404/403 的差异会变成订单号探测通道
    if order is None:
        raise ShopError("无权访问该订单", 403)
    if ctx.kind in ("service", "operator"):
        return order
    if order.user_id != _uid_of(db, ctx.cuid):
        raise ShopError("无权访问该订单", 403)
    return order

def _uid_of(db: Session, cuid: str) -> int:
    """cuid("u1001") → users.id(int)。复用既有 get_user()，不新造映射。"""
    return get_user(db, cuid).id
```

### 3.2 LLM 治理（改造 `ws/utils/llm_client.py` + 新增 `ws/utils/llm_guard.py`）

#### 3.2.1 常量（全部进 `settings`，不散落）

|---|---|---|
| 总预算 | `LLM_DEADLINE_SECONDS` | 20 |
| 单次上限 | `LLM_ATTEMPT_TIMEOUT` | 6 |
| 最大尝试 | `LLM_MAX_ATTEMPTS` | 3 |
| 退避 | `LLM_BACKOFF_SECONDS` | `0.5,1.0` |
| 流式首包 | `LLM_FIRST_TOKEN_TIMEOUT` | 5 |

#### 3.2.2 结构改造（解决 `with_retry` 重绑定问题）

```python
# llm_client.py
_raw_llm = init_chat_model(
    ...,
    temperature=1.1,
    timeout=settings.llm_attempt_timeout,   # 让 httpx 真正持有超时
    max_retries=0,                          # 关掉 SDK 自带重试，否则 3×3=9 次
)
llm = _raw_llm
```

重试上移到 `llm_guard`，理由：`with_retry` 退避无上限会击穿总预算；`langchain` 的 `RunnableConfig` **不支持 `timeout` 键**（传了会被静默丢弃），所以超时必须两处都做：SDK 层 `timeout=` + 外层 `asyncio.wait_for`。

#### 3.2.3 包装函数（对齐真实的 LCEL 调用形态，F-02）

| 函数 | 签名 | 说明 |
|---|---|---|
| `call_chain` | `async (chain, inputs: dict, *, trace_id: str) -> str` | 替代 8 处 `chain.ainvoke(x)`；内部 `await chain.ainvoke(inputs, config={"timeout": budget})` |
| `stream_chain` | `async (chain, inputs: dict, *, trace_id: str) -> AsyncIterator[str]` | 替代 5 处 `chain.astream(x)`；首包 5s；**不重试** |
| `_record` | `(stat: LlmCallStat) -> None` | 写日志 + 累加指标 |

```python
async def call_chain(chain, inputs, *, trace_id):
    deadline = monotonic() + settings.llm_deadline_seconds
    attempts = 0
    for wait in (0, *settings.llm_backoff_seconds):
        budget = min(settings.llm_attempt_timeout, deadline - monotonic())
        if budget <= 0:
            break
        attempts += 1
        if wait:
            await asyncio.sleep(wait)
        try:
            resp = await asyncio.wait_for(
                chain.ainvoke(inputs), timeout=budget)   # 不用 config 传 timeout（会被丢弃）
            _record(LlmCallStat(attempts=attempts, degraded=False, trace_id=trace_id))
            return resp
        except asyncio.TimeoutError:
            continue
        except APIStatusError as exc:          # 5xx 重试，4xx 不重试
            if exc.status_code < 500:
                raise
            continue
        except APIConnectionError:
            continue
    _record(LlmCallStat(attempts=attempts, degraded=True, trace_id=trace_id))
    logger.warning("llm.degraded trace_id=%s attempts=%d", trace_id, attempts)
    return FALLBACK_TEXT
```

要点：

- 异常必须捕 `openai.APIStatusError` / `APIConnectionError`（`init_chat_model` 底层是 openai SDK，**抛不出 httpx 异常**；项目自己的 `ws/utils/llm_errors.py` 也只能按类名字符串判断，可作旁证）；
- `config={"timeout": budget}` 让 SDK 真正断开 socket，而不是只取消外层协程；
- 流式必须 `try/finally: await agen.aclose()`，否则黑洞 base_url 下连接数会线性上涨直到 `PoolTimeout`。

```python
async def stream_chain(chain, inputs, *, trace_id):
    agen = chain.astream(inputs)
    try:
        first = await asyncio.wait_for(
            asyncio.shield(agen.__anext__()),
            timeout=settings.llm_first_token_timeout)
        yield first
        async for chunk in agen:
            yield chunk
    except asyncio.TimeoutError:
        yield FALLBACK_TEXT
    finally:
        # 必须在 finally：客户端断开（GeneratorExit）时也要关上游流，
        # 否则黑洞 base_url 下连接数线性上涨直到 PoolTimeout
        try:
```

### 3.3 幂等（D3=A，新增 `app/idempotency.py`）

#### 3.3.1 接口

```python
class Acquired(NamedTuple):
    ok: bool
    state: str          # "acquired" | "succeeded" | "in_progress"

def try_acquire(db, scope: str, key: str) -> Acquired
def mark_succeeded(db, scope: str, key: str, result_ref: str) -> None   # 业务事务内
def mark_failed(db, scope: str, key: str, reason: str) -> None          # 独立 Session
```

#### 3.3.2 抢占 SQL（唯一权威）

```sql
UPDATE idempotency_key
   SET status='processing', updated_at=now(), attempts=attempts+1
 WHERE scope=:scope AND key=:key
   AND ( status='failed'
         OR (status='processing' AND updated_at < now() - interval '5 minutes') )
RETURNING result_ref;
```

插入与抢占合并在 `try_acquire` 内：先 `INSERT ... ON CONFLICT DO NOTHING`，影响行数 1 即 `acquired`；否则跑上面这条，0 行则读状态返回 `succeeded`/`in_progress`。

#### 3.3.3 `create_order` 改造（关键：事务边界）

```python
def create_order(db, user, address_id=None, coupon_code=None, items=None,
                 request_id: str | None = None) -> OrderCreatedData:
    # ① 幂等占位（独立事务提交，让并发方可见）
    if request_id:
        acq = try_acquire(db, "order", request_id)
        if acq.state == "succeeded":
            return _order_dto(db, acq.result_ref)          # 回放，不碰库存
        if acq.state == "in_progress":
            raise ShopError("请求处理中，请勿重复提交", 409)
        db.commit()

    # ② 进入业务事务（内部不再 commit）
    try:
        order = _do_create_order(db, user, address_id, coupon_code, items,
                                 request_id=request_id)    # 传入 request_id
        if request_id:
            mark_succeeded(db, "order", request_id, order.order_id)
        db.commit()                                        # 唯一一次提交
        return _order_dto(db, order.order_id)
    except IntegrityError as exc:
        db.rollback()
        if request_id and "orders_request_id_key" in str(exc.orig):
            row = (db.query(models.Order)
                     .filter_by(request_id=request_id).one_or_none())
            if row is None:
                raise ShopError("下单冲突，请重试", 409)
            mark_succeeded(db, "order", request_id, row.order_id)
            db.commit()
            return _order_dto(db, row.order_id)
        _fail("order", request_id, "integrity_error")
        raise
    except ShopError:
        db.rollback()
        _fail("order", request_id, "business_error")            # 业务失败可重试
        raise                                              # 409/400 原样透出
    except Exception:
        db.rollback()
        _fail("order", request_id, "internal_error")
        raise
```

必须遵守（审查发现）：

1. `_do_create_order` 必须新增 `request_id` 形参，并在 `models.Order(...)` 构造时落库 —— 否则 `orders.request_id` 恒 NULL，唯一索引永不触发；
2. 原函数体内的 `db.commit()`（`shop_service.py:662`）与 `auto_close_expired_orders` 的提交必须下沉/前置，**业务路径只允许一次提交**；
3. `except IntegrityError` 必须写在 `except Exception` **之前**（Python 按顺序匹配，否则唯一冲突永远进不到该分支）；
4. `except ShopError` 单独处理，**不能**把它当系统错误吞掉或 500；同时 `mark_failed` 使同一 request_id 可重试；
5. `mark_failed` 用**独立 `SessionLocal()`** 并 `try/except` 包裹，失败只记日志，不掩盖原始异常；
6. 抢占后、库存校验前先做快速回放 `SELECT 1 FROM orders WHERE request_id=:k`，避免"先撞库存不足再撞唯一索引"返回 409 而订单其实已存在。
7. `_fail` 是**辅助函数**，不在主 Session 上执行：签名 `_fail(scope: str, key: str | None, reason: str)`，内部用 `SessionLocal()` 并 `try/except` 包裹；`key is None` 时直接 return。V1.1 正文里 `_fail(db, request_id, ...)` 共用主 Session 与「独立 Session」的声明矛盾，已统一。
8. **租约需要心跳**：抢占后 `updated_at` 若不再刷新，任何超过 5 分钟的慢请求都会被第二方"合法抢占"，两个事务同时带同一 `request_id` 进业务。措施：①业务事务每 60s（或每次外部调用前）`UPDATE idempotency_key SET updated_at=now() WHERE scope=:s AND key=:k`；②抢占语句加 `SET LOCAL lock_timeout='2s'`，避免长等；③最终仍以 `orders_request_id_key` 为准，先到者成功、后到者走 IntegrityError 回放。

```python
_trace_id: ContextVar[str] = ContextVar("trace_id", default="-")

class TraceMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        tid = request.headers.get("X-Trace-Id") or uuid.uuid4().hex[:16]
```

```sql
ALTER TABLE orders ADD COLUMN request_id varchar(64) NULL;
CREATE UNIQUE INDEX orders_request_id_key ON orders (request_id);
```

> `request_id` 可空是**有意为之**：历史订单为 NULL，PG 唯一索引对多 NULL 不冲突；仅新请求写入该列。

CHECK 约束见 §3.7.4（`NOT VALID` + `VALIDATE`）。

### 5.1 鉴权矩阵（8 类，对齐 CSC-HL-002 §5.1）

### 5.2 下单接口

| 项 | 内容 |
|---|---|
| 方法/路径 | `POST /shop/orders` |
| 请求头 | `X-Request-Id`（可选，≤64 字符）；`X-Service-Token` 或 `Authorization` |
| 请求体 | `{user_id, address_id?, coupon_code?, items?: [{sku_code, quantity}]}` |
| 200 | `{code:0, message:"ok", data:{order_id, pay_amount, coupon_code, expires_in_minutes, ...}}` |
| 409 | 幂等进行中 / 状态冲突 |
| 403 | 归属校验失败 |
| 401 | 凭证缺失或无效 |

### 5.3 错误码

| 码 | 场景 | 判定 |
|---|---|---|
| 400 | 参数错误、业务规则不满足（`ShopError` 默认） | — |
| 401 | 无/错凭证 | — |
| 403 | 角色不足或归属不符 | — |
| 409 | 幂等进行中、非法状态跃迁 | — |
| 429 | P2 限流 | — |
| 503 | LLM 全部尝试失败且降级话术也未能返回（如客户端已断开） | `llm_fallback_total` 增长但不影响 200 路径 |

## 6 出错处理（对应 CSC-HL-002 §8 的 12 类场景）

| 场景 | 检测 | 处置 |
|---|---|---|
| LLM 超时 | 预算耗尽 | 降级话术 + `llm_fallback_total` |
| 流式首包超时 | 5s 无首 token | 发降级事件后 `aclose()` 上游流 |
| 中台不可用 | 连接失败/5xx/10s | 503 + 「系统繁忙」 |
| 备份失败 | 退出码≠0 或 ≤1KB | 不更新 `last_success`，保留旧备份 |
| 恢复失败 | 校验行数不符 | 保留临时库，换备份点重试 |
| 迁移失败 | `alembic upgrade` 非 0 | 停止发布，镜像保持旧版本 |
| 迁移脏数据 | 前置查询有行 | `RuntimeError` 中止，不写 schema |
| OOM | 容器被杀 | 按 postgres→ecommerce→backend→frontend 重启 |
| 鉴权误配 | smoke 登录/对话失败 | `rollback.sh` |
| 审计写失败 | 插入异常 | 业务事务回滚 |
| PG 连接耗尽 | 连接异常激增 | 503 + 重启 backend |
| 令牌轮换 | 401 突增 | 新旧令牌并存 7 天 |

## 11 限制条件

| 类别 | 限制 |
|---|---|
| 运行环境 | 单台阿里云 2C2G（可用 1.75G）；单实例、无多副本；Python 3.12；PostgreSQL 16 + pgvector + pg_trgm；Node 22 |
| 并发 | Agent 单 worker；PG `max_connections=50`；SSE 长连接数量受 worker 限制 |
| 数据量 | 订单 < 10 万行、知识条目 < 1 万条；超此量级需重新评估索引与迁移锁策略 |
| 迁移 | 不允许在线对大表做 `ACCESS EXCLUSIVE`；必须 `NOT VALID` + `VALIDATE` 分两步 |
| 网络 | LLM 为外部依赖，单轮预算 20s；中台调用超时 10s；LLM 不可用时必须降级而非阻塞 |
| 事务 | 不做跨库事务（`customer_service` 与 `commerce` 两库）；幂等只在单库内保证 |
| 依赖 | 新增依赖仅 `pyjwt`、`alembic`；不得引入常驻监控组件（见 CSC-FS-001 C-01） |
| 兼容 | 旧 JWT（无 `cuid`）不再兼容，上线后需重新登录一次；旧订单 `request_id` 为 NULL 不参与幂等 |
