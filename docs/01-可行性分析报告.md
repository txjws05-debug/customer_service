## 1 引言

### 1.1 编写目的

本报告用于论证「将现有电商智能客服系统从演示级项目改造为工程级系统」的可行性，明确改造范围、技术路径、资源投入与主要风险，为后续《概要设计说明书》《详细设计说明书》《测试计划》的编制提供依据，并作为改造启动的决策材料。

读者：项目负责人（决策）、开发人员（执行依据）、评审人（技术与管理评审）。

### 1.2 项目背景

现有系统已实现完整业务闭环：用户可在同一对话框内完成「问规则 → 查订单物流 → 加购下单支付 → 申请售后」，后台是包含商品/库存、购物车、订单状态机、支付、履约、优惠券积分、售后、评价、运营看板的电商中台。

系统已具备相当的工程质量：客服端 102 个测试函数（pytest 收集 117 项）、中台 63 个用例（跑在真实 PostgreSQL 上）；41 条标注集的检索评测（曾记录 Recall@1 91.7% → 100%，属历史手工评测，仓库未留存评测产物）；10 并发抢 3 件商品的超卖验证；Redis 读缓存命中率 99.0%；CI 构建 → GHCR → SSH 部署 → 部署后自检的完整流水线。

**但系统缺少四类「工程级系统必备」的能力**：接入边界（鉴权/限流）、运行时观测（指标/追踪/成本）、数据生命周期（迁移/备份/恢复）、失败态设计（超时/重试/降级/幂等）。此外，对话层直接持有业务实体的裸 id，存在跨轮状态耦合。

这些问题不影响演示，但决定了系统能否被第三方攻击、运维、审计与长期维护。

## 2 现状与问题定义

本章问题均来自对线上环境（http://txjws.dpdns.org）与源码的实际核查，非推测。

### 2.1 能力盘点

| 层级 | 已有能力 | 缺口 |
|---|---|---|
| 接入层 | Caddy 反代、自动 HTTPS、SSE 透传 | 中台鉴权、限流、配额 |
| 对话层 | 意图路由、RAG 检索、任务槽位、流式输出 | LLM 超时/重试/降级、成本记录 |
| 业务层 | 下单、支付、履约、售后、优惠券积分；订单与售后双状态机（`shop_rules.py`，含跃迁白名单与校验函数） | 幂等键、状态约束下沉到数据库、状态机缺少直接单测 |
| 数据层 | PostgreSQL 16 + pgvector + pg_trgm | 迁移框架、备份恢复、回滚 |
| 观测层 | 应用日志（logging） | 指标、链路追踪 |

### 2.2 问题清单与证据

| 编号 | 问题 | 实测证据 | 严重度 |
|---|---|---|---|
| P-01 | 中台接口无鉴权 | `GET /shop/admin/orders` 匿名访问返回 HTTP 200，包含全站 12 笔订单的昵称与支付金额；源码 `ecommerce-service-backend/app/` 中无任何鉴权依赖 | 严重 |
| P-02 | API 文档公开 | `GET /docs` 匿名返回 200 | 中 |
| P-03 | 无运行时可观测性 | 全仓检索 `prometheus`/`opentelemetry`/`structlog` 均无结果 | 严重 |
| P-04 | LLM 生成链路无超时、退避无上限 | `llm_client.py` 已有 `with_retry(stop_after_attempt=2, wait_exponential_jitter=True)`，即**有重试但无 timeout、退避无上限**；另有 `embedding.py`（30s）与 `utils/http.py`（中台调用 10s）两处固定超时 | 严重 |
| P-05 | 无数据备份与恢复机制 | `deploy/` 下无备份脚本；数据位于裸 volume `pgdata` | 严重 |
| P-06 | 无迁移框架 | 依赖 `Base.metadata.create_all` + `ADD COLUMN IF NOT EXISTS` 补列 | 中 |
| P-07 | 无回滚能力 | `deploy/` 仅有正向部署脚本；镜像 tag 已按 commit sha 保留，但无回滚脚本 | 中 |
| P-08 | 状态跃迁约束仅在应用层，未穷举验证 | `shop_rules.py` 已有两套状态机与校验函数，`tests/test_shop_rules.py` 也已有 5 组直接单测；但非法组合仅覆盖 4+2 条，**未做 7×7 全组合穷举**，且数据库层无 CHECK 约束（应用层绕过即失效） | 轻 |
| P-09 | 对话状态与业务实体耦合 | `focuse_object` 原先无类型约束，订单 id 可被当商品 id 查询（已线上热修并加 `focused_id_of` 类型校验，但该修改尚未入库，且无 schema 级约束） | 中 |
| P-10 | 下单无幂等 | `orders` 表无 `request_id` 字段；重复提交会重复建单 | 严重 |
| P-11 | **无对象级授权（越权）** | `_get_order` 只按 `order_id` 查、不带 user 过滤（`shop_service.py:676-690`）；任意登录用户凭订单号可读他人收货人姓名/地址/金额，或取消/支付/收货他人订单；下单接口 `user_id` 取自信任的请求体。**加鉴权也挡不住这类越权** | 严重 |

### 2.3 问题对项目价值的影响

前四类问题（P-01～P-05）的共同特征是：**不影响功能正确性，但决定系统能否被信任**。在技术评审或面试场景中，P-01 只需一条 curl 命令即可暴露，属于「一句话否定整个项目」的风险。

## 3 目标与范围

### 3.1 本期目标

在**不重写、不拆分服务、不更换技术栈**的前提下，使系统达到以下可验证状态：

1. 所有对外接口有明确访问边界，匿名请求无法读写业务数据；
2. 系统具备指标、日志、成本三条可观测线；
3. 数据具备迁移、备份、恢复、回滚四项生命周期能力；
4. 关键写路径具备幂等性，非法状态跃迁在结构上被拒绝；
5. 多轮任务具备回归评测能力，且进入 CI。

### 3.2 范围边界

**纳入范围**：接入鉴权、限流与配额、LLM 调用治理、结构化日志与链路追踪、指标暴露、订单状态机、幂等键、数据库迁移、备份恢复、部署回滚、多轮对话评测集。

**不纳入范围**（明确排除，理由见 4.4）：

- 微服务拆分与容器编排升级（K8s）
- 真实支付渠道接入
- 多租户与计费体系
- 模型微调
- 前端重写

### 3.3 约束条件

| 约束 | 内容 | 影响 |
|---|---|---|
| C-01 | 运行环境为单台阿里云 2C2G（可用内存 1.75G） | 禁止在该机构建前端镜像；**不可引入 Prometheus + Grafana 等常驻重型监控栈**（约 300MB，占可用内存 17%）；新增能力原则上非常驻 |
| C-02 | 单机 6 个服务（5 个业务容器 + 1 个反代），单机部署 | 高可用不做，只保证可恢复（RTO/RPO 目标见 3.4） |
| C-03 | 单一维护者，开发过程重度使用 AI 辅助 | 方案复杂度必须可控，避免引入无人能维护的组件 |
| C-04 | 当前 GitHub 访问受限，CI/CD 暂时不可用 | 改造需支持「不依赖 CI 的热更新路径」作为过渡 |

### 3.4 非功能目标（本期）

| 指标 | 目标值 | 当前值 |
|---|---|---|
| 单轮对话 P95 延迟 | ≤ 8s | 未测量 |
| LLM 超时后接口响应 | ≤ 25s 内返回降级话术 | 无上限（可能挂死） |
| 备份 RPO | ≤ 24h | 无备份 |
| 恢复 RTO | ≤ 30min | 不可恢复 |
| 部署回滚耗时 | ≤ 3min | 无回滚手段 |
| 匿名访问写接口与运营接口 | 全部 401/403（公开商品浏览除外） | 200 |
| 多轮任务评测覆盖（P1 末） | ≥ 20 条脚本化对话，绝对通过率 ≥90% | 0 |

## 4 可行性分析

### 4.1 方案比较

| 方案 | 描述 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A 渐进改造 | 在现有代码基线上按 P0→P1→P2 分批改造，每批可独立上线与回滚 | 风险可控、每步有可展示成果、不中断线上服务 | 需处理历史包袱（如焦点对象耦合） | **推荐** |
| B 重构重写 | 保留业务模型，重写对话引擎与中台 | 架构更干净 | 工期 ≥ 3 个月，期间线上不可用；单人重写风险极高；已有 180 个测试项（Agent 117 + 中台 63）与评测资产需重建 | 否决 |
| C 维持现状 | 仅修复缺陷，不做系统性改造 | 零成本 | 无法解决 2.2 中严重级问题，项目停留在演示级 | 否决 |

**选 A 的理由**：现有系统的业务实现与测试资产是可复用的存量价值，问题集中在「外围能力缺失」而非「核心设计错误」。渐进改造能用最小代价补齐外围，同时保留已有证据链。

### 4.2 技术可行性

#### 4.2.1 技术栈匹配度

| 改造项 | 现有技术栈是否支持 | 说明 |
|---|---|---|
| 中台鉴权 | 支持 | FastAPI `Depends` 机制成熟，新增依赖注入即可，无需改路由结构 |
| 运营端权限 | 支持 | 前端已有 `/admin` 页面，后端已有 `/shop/admin` 路由前缀，可按前缀挂鉴权 |
| LLM 治理 | 支持 | 现用 LangChain + OpenAI 兼容接口，`timeout`/`max_retries` 为原生参数 |
| 结构化日志 | 支持 | 现用标准库 `logging`，替换 Formatter 即可输出 JSON，无需引入新框架 |
| 链路追踪 | 支持 | 中台与 Agent 均为 HTTP 调用，`httpx` 支持透传 header |
| 指标暴露 | 支持 | 可手写 Prometheus 文本格式（约 50 行），不引入依赖 |
| 订单状态机 | 已具备，需加固 | `shop_rules.py` 已有订单与售后两套状态机的白名单与校验函数；本期只补数据库 CHECK 约束与白名单单测，不新建 |
| 幂等键 | 支持 | `orders` 表需新增 `request_id` 列与唯一索引；幂等记录表为本期新建 |
| Alembic | 支持 | SQLAlchemy 2.x，Alembic 为同生态标准工具，可生成 baseline |
| 备份恢复 | 支持 | `pg_dump`/`pg_restore` 容器内可用，配 cron 即可 |
| 多轮评测 | 支持，但需新写 runner | 现有 `ws/knowledge/eval.py` 只支持单轮标注集（JSON、按 doc_id 断言），任务级用例需独立 runner，仅复用其 CLI 骨架与结算结构；CI 当前不可用，首轮在服务器手工执行并归档报告 |

**结论**：全部改造项均可在现有技术栈内完成，无一项需要引入新技术体系。

#### 4.2.2 已验证的技术结论

以下结论来自本项目已有实测，可作为改造的技术依据：

| 结论 | 数据来源 |
|---|---|
| 单机 2C2G 可承载当前负载 | 线上稳定运行 3 周，6 个服务（5 业务容器 + 反代）健康 |
| PostgreSQL 行锁可防超卖 | 10 并发抢 3 件 → 恰好 3 单成功、库存归零 |
| 检索改动可被量化验证 | Recall@1 91.7% → 100%，MRR 0.949 → 1.000（历史手工评测，仓库无留存产物） |
| 缓存只加速读不影响正确性 | 命中率 99.0%，吞吐 350.9 → 435.6 req/s |
| CI 到部署的链路可用（当前受限除外） | GHCR 三镜像 `latest` 摘要与 `main@3874fa4` 一致 |

#### 4.2.3 主要技术难点

| 难点 | 分析 | 对策 |
|---|---|---|
| T-01 鉴权改造会中断现有调用链 | Agent→中台为内网调用，加 token 后若漏配会导致全部业务失败 | 分两步：先加「允许列表」放行现有调用并记录，再强制校验；保留环境变量开关用于回退 |
| T-02 焦点对象重构影响面大 | `focuse_object` 被 `task/`、`plan/`、`knowledge/` 多处引用 | 本期只做类型化与校验（已部分落地），完整上下文建模放到 P1 末；用现有 180 个测试项作为回归网 |
| T-03 单机无法部署重型监控 | 内存仅 1.75G，Grafana + Prometheus 常驻约 300MB+ | 只暴露 `/metrics` 端点，采集与展示放到外部或按需启动，不常驻 |
| T-04 本地无 Docker，无法本地跑集成测试 | 依赖真实 PostgreSQL 的测试无法在本机运行 | 测试统一在服务器或在 CI 上执行；本地仅做单元测试与语法/静态检查 |

### 4.3 经济可行性

#### 4.3.1 成本构成

| 项目 | 金额 | 说明 |
|---|---|---|
| 服务器 | ¥0 增量 | 复用现有闲置阿里云 2C2G，无新增支出 |
| 镜像仓库 | ¥0 | GHCR 公开包，免费额度内 |
| 域名 | ¥0 增量 | 使用现有 `txjws.dpdns.org`（免费动态域名） |
| LLM 调用 | 见下式估算 | DeepSeek 兼容接口，按 token 计费 |
| 人力 | 单人，约 37 人日 | P0 6 + P1 14 + P2 12 + 缓冲 5 = 37 天 |

LLM 成本估算式（单价以实际账单为准，此处仅作量级判断）：

```
单轮对话 token ≈ 上下文 2,000 ～ 3,500 + 输出 200 ～ 400
日对话量假设   ≈ 100 轮（自用与演示场景）
月 token 量    ≈ 100 × 3,000 × 30 ≈ 9M tokens/月
```

按主流国产模型每百万 token 个位数人民币量级的定价，月成本在**数十元以内**。即使在压测场景下放大 10 倍，仍在可接受范围。

#### 4.3.2 收益

**直接收益（工程）**

1. 消除 P-01 这类「一句话否决」的暴露面；
2. 故障可定位（trace_id + 指标）、数据可恢复（备份）、发布可回退（sha 回滚）；
3. 成本可计量，避免 API Key 被刷爆产生意外账单。

**间接收益（项目价值）**

1. 形成可展示的证据链：401 前后对比、恢复演练耗时、幂等收敛验证、多轮任务成功率曲线；
2. 提供「判断变化」的叙事素材：例如 Alembic 的取舍从「不用」改为「用」，并说明触发条件；
3. 覆盖面试高频追问：权限边界、幂等、可观测性、失败态、数据安全。

#### 4.3.3 成本收益判断

投入约 37 人日（32 天工作 + 5 天缓冲）、月增成本数十元，换取系统从「演示级」到「可运维级」的跃迁，**投入产出比合理**。相较方案 B（重写，≥3 个月），方案 A 用约 2/5 的工期达成同等的外部可验证效果。

## 6 结论与建议

### 6.1 结论

1. **技术可行**：全部改造项在现有技术栈内可完成，无新技术体系引入；关键能力（PG 行锁、pgvector、CI 部署、2C2G 承载）均已有实测支撑。
2. **经济可行**：无新增基础设施支出，人力投入约 37 人日（32 天工作 + 5 天缓冲），LLM 月成本在数十元量级。
3. **操作可行**：改造以脚本与端点为主，不引入常驻重型组件，符合单机与单人维护约束。
4. **进度可行**：三阶段共 37 天（含缓冲），关键路径明确。
5. **风险可控**：8 项风险均有对应措施，其中 R-02（CI 不可用）与 R-04（备份未演练）需在实施中特别跟踪。

**综合判断：本项目具备实施条件，建议按方案 A 启动改造。**

### 6.2 建议

1. **先做 P0 第 1 项（中台鉴权）**：1 天工作量，直接消除最高暴露风险，且可作为后续改造的灰度范例。
2. **备份脚本与恢复演练必须同批交付**：只写脚本不演练，等于没有备份。
3. **每项改造单独发布**：与其一次性上线五项，不如五次各上线一项，每次都有独立回退点。
4. **P2 可裁剪**：多轮任务评测已前移 P1 并视为必做（可量化、可展示）；若工期不足，优先裁剪「知识库管理 UI」（可用命令行替代）。
