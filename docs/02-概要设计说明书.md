## 2 总体设计

### 2.1 设计原则

| 编号 | 原则 | 含义 |
|---|---|---|
| D-01 | 边界内建 | 鉴权与校验写在框架层（依赖注入、中间件），不依赖每个接口自觉调用 |
| D-02 | 最小依赖 | 新增能力优先用标准库或手写实现，禁止为单一功能引入重型框架 |
| D-03 | 可回退 | 每项改造提供独立回退手段（env 开关 / 镜像 tag / 迁移 downgrade） |
| D-04 | 证据驱动 | 每个设计点必须有可验证的验收方式 |
| D-05 | 单机优先 | 新增组件默认非常驻、无状态；受 1.75G 内存约束 |
| D-06 | 不重建已正确的东西 | 已有能力（双状态机、行锁防超卖、RAG 评测框架）只加固不重写 |

### 2.2 逻辑架构

```
【接入层】 Caddy（TLS、反向代理、SSE 透传、/shop/admin 访问控制）
              ↓
【对话层】 ws/api → ws/engine → ws/plan → ws/task
           ws/knowledge（RAG）｜ws/clarify｜ws/chitchat
           + LLM 治理（预算 / 重试 / 降级 / 计量）
              ↓
【业务层】 中台 shop_api｜shop_admin_api｜shop_after_sale_api

【数据层】 PostgreSQL 16（双库）｜pgvector + pg_trgm｜Redis（只读缓存）

贯穿本期：trace_id 全链路 ｜ 审计留痕 ｜ 多轮任务评测
```

## 4 关键流程设计

### 4.1 鉴权设计

**四级访问主体：**

| 主体 | 凭证 | 可访问 | 校验点 |
|---|---|---|---|
| 匿名 | 无 | `/api/auth/*`、`/shop/products`、`/shop/categories`、静态资源 | — |
| 登录用户 | `Authorization: Bearer <JWT>` | `/api/*`、`/shop` 写接口 | Agent `get_current_user`；中台 `require_user` |
| 服务（Agent→中台） | `X-Service-Token` | 中台 `/`（C 端基础接口） | 中台 `require_service_token` |
| 运营人员 | `X-Operator-Token` 静态令牌 | `/shop/admin/*` | 中台 `require_operator` |

> V1.5 修订：中台无 JWT 签发能力，故 operator 改用**静态令牌**（env 配置、可轮换）；普通用户 JWT 由中台**仅校验**（新增 `pyjwt` 依赖）。另新增**对象级授权**一层：用户只能访问自己的订单与账户资源，服务令牌与 operator 可跨用户。详见 CSC-DD-003 §3.1。

**开关与灰度（应对 R-01）：**

- `AUTH_ENFORCE` 取值 `on`（默认）/ `warn` / `off`。
- `warn` 仅用于部署窗口内的观察：校验失败记录日志后放行。**启动时强制检查**：若 `warn` 持续超过 24 小时，进程自动切 `on` 并在日志中记录 `auth.warn_expired`。
- `off` 仅允许在本地开发环境使用，生产环境检测到 `off` 时启动失败（fail-fast），避免误配置长期裸奔。
- 回退手段：镜像回滚到上一版本（`rollback.sh`），而非长期依赖开关。

### 4.2 对话主流程与观测点

```
客户端 → Caddy → Agent /api/chat
 ① 中间件生成或沿用 X-Trace-Id
 ② JWT 鉴权 → current_user
 ③ dialogue_engine 分流：对象 / 任务 / 知识 / 闲聊
 ④ 知识路径：provider 检索 → LLM 生成（受 4.3 约束）
 ⑤ 任务路径：槽位填充 → 调中台（携带 trace_id 与 X-Service-Token）
 ⑥ 响应：完整文本或 SSE 增量（流式路径不重试，首包 5s 未到即降级）
 ⑦ 日志：trace_id / 用户 / 意图 / 耗时 / token / 是否降级
```

### 4.3 LLM 调用治理

采用**总预算（deadline）**而非「单次超时 × 重试次数」，避免最坏耗时突破上限：

| 参数 | 取值 | 说明 |
|---|---|---|
| 端到端预算 | 20s | 从发起首次调用开始计时，所有重试共享 |
| 单次超时 | 6s | 单次请求上限，且不超过剩余预算 |
| 最大尝试次数 | 3（首次 + 2 次重试） | 仅网络错误与 5xx 重试，4xx 不重试 |
| 退避 | 0.5s、1s | 计入总预算 |
| 首包超时（流式） | 5s | 首 token 未到达即放弃；**流式路径不参与重试**，避免超出总预算 |
| 超预算处置 | 返回降级话术 | 例：「这会儿有点忙，稍后再问我一次？」 |
| 计量 | model / prompt_tokens / completion_tokens / 耗时 / 是否降级 | 汇总进 `/metrics` |

**最坏耗时核算**：非流式路径 6 + 0.5 + 6 + 1 + 6 = 19.5s ≤ 20s 预算；流式路径不重试，5s 首包超时即降级（远低于预算）。两条路径加序列化与网络开销后均 ≤ 25s，满足 CSC-FS-001 §3.4。

为保证约束落地，新增 `ws/utils/llm_guard.py` 包装 **13 个 LCEL 调用点**（6 个文件：chitchat 2、clarify 2、knowledge/responder 2、plan/turn_plan 2、history_compactor 1、task/response/render 4），逐个替换 `chain.ainvoke/astream`，**不是"加个单例就自动生效"**。

### 4.4 幂等下单流程

**占位与收敛（并发安全）**

```
提交下单(request_id, items)
 ① request_id 缺失 → **不启用幂等**，按原路径执行（保持现状兼容；是否强制由 DQ-05 决定）
 ② 尝试占位：INSERT INTO idempotency_key(scope='order', key=request_id, status='processing')
    ON CONFLICT (scope, key) DO NOTHING
    ├─ 影响行数=1 → 本次持有执行权，转 ③
    └─ 影响行数=0 → 执行统一的「抢占」语句（见下）
         ├─ 抢占成功（影响行数=1）→ 转 ③
         └─ 抢占失败（影响行数=0）→ 读现有记录：
             ├─ succeeded → 200，返回 result_ref（幂等命中，不重复扣库存）
             └─ 其他 → 409「请求处理中，请勿重复提交」

 抢占语句（failed 与租约过期的 processing 用同一条，避免两套时基）：
   UPDATE idempotency_key
      SET status='processing', updated_at=now()
    WHERE scope='order' AND key=?
      AND ( status='failed'
            OR (status='processing' AND updated_at < now() - interval '5 minutes') )
   → 影响行数=1 才算抢到；=0 说明有人正在跑且租约未过期

 ③ 业务事务：校验库存 → 行锁扣减 → 建订单 → 建订单项
    成功 → 同一事务内 UPDATE idempotency_key SET status='succeeded', result_ref=<order_id>
    失败 → 业务事务回滚；随后独立写入 status='failed'（保留可重试）
 ④ 响应：返回 order_id
```

要点：

- **唯一索引 `(scope, key)` 是幂等的最终保证**，应用层判断只负责友好返回；
- 抢占统一在一条 SQL 里完成，**不在应用侧比较时间**：应用时钟与数据库时钟不同源，分开判断会在边界上产生空转或提前 409；
- 谓词里带 `updated_at < now() - interval '5 minutes'` 是必需的：若只按 `status='processing'` 判断，PostgreSQL 在 READ COMMITTED 下会对阻塞后的语句重检谓词，谓词仍为真，两个会话都拿到「影响行数=1」而双双执行 —— 这是本节初稿的缺陷；
- **租约只能防「同时抢占」，防不了「原持有者跑得太久」**：若一次下单事务执行超过 5 分钟，新请求仍可抢到租约并再执行一遍。因此最终兜底是 `orders.request_id` 唯一索引（§6.3），业务层重复建单会被数据库拒绝，而不是靠租约保证。

### 4.5 订单与售后状态机（已存在，本期加固）

**事实澄清**：`shop_rules.py` 已实现两套完整状态机，含跃迁白名单与校验函数，且发货、确认收货路径已调用。本期不新建状态机，只做三件事：补数据库约束、补白名单单测、收敛剩余裸判断。

**订单状态（7 个，取自 `shop_rules.py`）**

| 当前状态 | 允许到达 | 触发动作 |
|---|---|---|
| 待付款 | 待发货、已取消 | 支付成功、超时关单、用户取消 |
| 待发货 | 待揽收、已取消 | 发货、用户取消 |
| 待揽收 | 运输中 | 物流交接 |
| 运输中 | 待收货 | 到达 |
| 待收货 | 已完成 | 确认收货 |
| 已完成 | ∅ | — |
| 已取消 | ∅ | — |

> 注意：`已付款，商家备货中。` 是**「待发货」的描述文案**（`STATUS_DESC`），不是独立状态。V1.0 文档曾把它当作状态，已更正。

**售后状态（7 个）**：`submitted → approved → returning → received → completed`，另有 `rejected`、`canceled` 终态；另有三条捷径/旁支边：`approved → canceled`（审核后用户撤销）、`received → rejected`（收到退货但验收不通过）、`approved → completed`（仅退款，跳过退货）。退款申请（`refund_requests`）为第三套独立状态，本期不改。实现以 `AFTER_SALE_TRANSITIONS` 为准，文档的线性描述仅作概览。

**本期加固内容**

1. 数据库层加 CHECK 约束，把 7 个订单状态固化（售后状态同理）；
2. 把现有 5 组直接单测升级为**参数化穷举**（7 个状态 × 7 个状态的合法性全覆盖，售后同理）；
3. 清理剩余裸字符串判断（当前主要残留在商品/优惠券状态，非订单状态）。

### 4.7 备份与恢复

```
每日 03:00 cron → backup.sh
 ① pg_dump -Fc 两库 → /var/backups/csc/YYYYMMDD/*.dump
 ② 校验：退出码=0 且文件 > 1KB，否则视为失败，不更新 last_success
 ③ 保留 7 天，超出删除
 ④ 写 last_success（时间 + 大小 + 校验和）

演练/恢复 → restore.sh <date>
 ① 建临时库 csc_restore_test
 ② pg_restore → 校验：关键表行数、最新订单存在、知识库向量行数
 ③ 记录耗时到演练记录，删除临时库；校验失败则保留临时库供排查
```

### 4.8 发布与回滚

| 步骤 | 内容 |
|---|---|
| 发布通道 A（常态） | `git push` → CI 构建 → GHCR → SSH 部署（现有机制） |
| 发布通道 B（无 CI 时的过渡，对应 R-02） | 单文件级热更新：`docker cp` + `docker restart`，仅限补丁级改动；每次必须在 `CHANGELOG-hotfix.md` 记录文件、时间、回滚方式 |

> 通道 B 是过渡手段，不作为正式发布路径；其改动必须在 GitHub 恢复后补 commit 入库，否则下次通道 A 的 `git reset --hard` 会覆盖。

**发布纪律（对应 CSC-FS-001 R-06、R-07）**

- 每次发布只含**单一主题**：缺陷修复与改造不混在同一次发布（回滚时才能定位）；
- 每项改造随附本设计文档的对应小节 + 单测，无设计说明的改动不合入；
- 通道 B 的每次热更都要在 `CHANGELOG-hotfix.md` 记录：文件、时间、原因、回滚方式。

### 4.9 多轮任务评测设计

目标：把「能聊」变成「能证明任务被完成」。现有 41 条标注集只覆盖单轮检索，不覆盖任务闭环。

**用例结构**（`ws/knowledge/data/task_eval.yaml`）

```yaml
- name: 加购并下单成功
  preset: {user: new, product: SKU10001, sku: SKU10001-256}
  steps:
    - send: {text: "iPhone 15 Pro 多少钱"}
      expect: {contains: ["8999"]}
    - send: {text: "帮我加一个到购物车"}
      expect: {task_state: cart_pending}
    - send: {text: "结算，用满500减50的券"}
      expect: {task_state: checkout_confirming}
    - send: {text: "确认下单"}
      expect: {contains: ["订单"]}
  final:
    db: {orders_status: 待付款, coupon_used: true}
```

**断言维度（四类）**

| 类型 | 例子 | 作用 |
|---|---|---|
| 任务完成 | 下单后订单状态=待付款、金额正确 | 证明闭环 |
| 拒绝正确 | 超纲问题（「今天天气」）不编造 | 证明不幻觉 |
| 防串号 | 焦点为订单时问商品价，不得把订单号当商品 ID | 锁住刚修的缺陷 |
| 幂等 | 同 request_id 重复确认下单只产生 1 单 | 锁住 C-08 |

**执行与隔离**

- **不复用 `eval.py` 的加载与断言**：现有 `eval.py` 只认 `rag_eval.json`，并按 `doc_id` 校验命中，任务用例没有 `doc_id`，会被误判为超纲；因此新增独立 `task_eval` runner，**仅复用其 CLI 参数与结算骨架**，用例加载、断言、报告均重写。
- 直连 Agent HTTP 接口（`httpx`），不经过前端；
- 每条用例注册独立测试账号（`probe_<uuid>`），用例结束清理其订单与购物车数据，避免相互污染；
- **库存隔离**：下单会真实扣减库存且不回补，反复跑评测会把商品买空。因此评测使用**专用测试 SKU**（初始库存 9999，不对外展示），或每轮开始前重置库存；不得复用演示商品 SKU。
- 失败时保留 trace_id，可直接按 trace 查日志复盘。

**产出与门禁**

- 输出 `task_eval_report.json`（通过率、逐条结果、耗时）与一行汇总；
- **阈值分两级，不混用**：①首次交付要求绝对通过率 ≥90%；②此后以「首次连续 3 次的移动平均」归档为 `task_eval_baseline.json`，后续不得低于该基线的 95%；
- 新增用例单列分母，不计入存量通过率，避免「新增用例失败拉低整体」的歧义；
- CI 当前不可用（CSC-FS-001 C-04），**CI 恢复前由服务器手工执行并归档报告**作为等效验收；CI 恢复后接入为门禁。

## 8 出错处理设计

| 场景 | 检测方式 | 处置 | 恢复步骤 | 观测 |
|---|---|---|---|---|
| LLM 超时/失败 | 总预算 deadline 触发、HTTP 异常 | 返回降级话术，保留用户原问 | 自动，无需人工 | `llm_fallback_total` |
| 流式首包超时 | 5s 内无首 token | 以 SSE 发送降级话术事件后结束流（已发出的增量保留在会话历史） | 自动 | `llm_fallback_total` |
| 中台不可用 | 连接失败、5xx、10s 超时 | 返回「系统繁忙，请稍后」并记 503 | 查 `smoke.sh`，失败则 `rollback.sh` | 错误日志 + trace_id |
| 备份失败 | 退出码≠0 或文件 ≤1KB | 不更新 `last_success`，保留上次成功标记 | 次日重试；连续 2 次失败需人工介入 | cron 日志 + 文件时间戳 |
| 恢复失败 | 行数/关键数据校验不符 | 中止恢复，**保留临时库**供排查 | 换上一个备份点重试；禁止删库重来 | 演练记录 |
| 迁移失败 | `alembic upgrade` 报错 | 停止发布，容器保持旧版本 | `downgrade` 回退；仍失败则用备份恢复 | alembic 日志 |
| 迁移 downgrade 失败 | `downgrade` 报错 | **不手工改表** | 用备份恢复到升级前时点 | 演练记录 |
| 鉴权误配（R-01） | `smoke.sh` 登录或对话失败 | 立即 `rollback.sh` | 回滚镜像；排查 `X-Service-Token` | 401 比例突增 |
| PG 连接耗尽 | 连接异常激增 | 返回 503，拒绝新请求 | 重启 backend；检查连接泄漏 | 连接数指标 |
| 令牌轮换期 | 401 集中出现 | 新旧令牌并存校验 7 天 | 到期下线旧令牌 | 校验失败日志 |
| 内存不足（OOM） | 容器被杀、`dmesg` 出现 oom-kill | 按依赖顺序重启：postgres → ecommerce → backend → frontend；期间 503 | 复核 9.2 预算；若新增组件导致超限，先摘除该组件而非扩内存 | `docker stats` 快照 |
| 审计写入失败 | 插入异常 | 业务事务回滚（写操作不脱离审计） | 修复后重试；禁止「审计失败仍放行」 | 审计表自增断档 |
